Shared kernel and server cleanup

Task 016In progresschore/shared-kernel

A tidy-up of the parts of the server that every feature shares, and a fix for errors that came back without a code. There is nothing new to click in the app.

Try it

With the server running, ask for a URL that does not exist. Before this task the answer had no code, so the app would have said it could not reach the server:

curl -i localhost:8080/api/does-not-exist
# 404, and the body now says "code": "NOT_FOUND"

What was built

  • The shared parts are named for what they are. platform/core looked like the pure rules of a feature but held none. It is now platform/kernel and holds only the answer type Decision and the list of error codes Rejection (see the glossary).
  • The geometry rule has its own home. Wgs84 moved to a geo package. It now also owns the reference system itself (its number, 4326, and the factory that builds shapes in it), which used to be written out in three places.
  • The build guards both. Two architecture tests: code in kernel and geo uses no Spring, and neither may depend on a feature or on the server code around them.
  • One table of error answers. Each rejection's status, title and text used to sit in three separate lists. They are one list now, so a new error code is added once. The deprecated Spring name for status 422 is replaced (same number on the wire), and the five hand-written copies of "build an error response" became one helper.
  • Annotation status is typed. It was a free string. It is now DRAFT, PUBLISHED or ARCHIVED in the database mapping, the API contract and the generated client, so a typo no longer compiles and the mapper has no "unknown status" branch.
  • Small tidy-ups. Unused variables use Java's _. Import elements expose their tags directly, which removed a duplicate switch.

What changed in the answers

RequestBeforeNow
A URL that matches nothing404, no code in the body404 NOT_FOUND
A method the URL does not support405, no code in the body405 REQUEST_INVALID
A scene that does not exist, read on its own404 NOT_FOUND404 SCENE_NOT_FOUND, like every other endpoint

Found on the way

  • Errors from the framework carried no code. While reviewing, I read the error handler and concluded that an unknown URL got the code REQUEST_INVALID. A test written first showed it was worse: those answers had no code at all. Spring builds the body of such errors itself, so the handler never saw it. Every error is promised to have a code, and the app shows "Could not reach the server" when one is missing. Fixed.
  • My own claim was wrong, and the test caught it. That is why the change started with two failing tests, not with the fix.

Why it works this way

The reasoning and the alternatives are in ADR 0012. ADR 0011 now also says plainly that the import writes straight into the annotation table.

How it was checked

CheckResult
ErrorsTwo new tests (no route, wrong method) failed on the old code and pass now. The scene test expects the one scene code.
Architecture rules can failMaking a kernel class depend on the server code failed the new rule. Making Wgs84 import Spring failed the purity rule. Both were restored.
Whole suites192 backend tests (3 more than before) and 179 client tests pass. Formatting, lint and the production build are clean.
ContractThe only differences in the API contract are the status values and one corrected description. The client was regenerated and one test fixture needed a more precise type.

Known limits

  • Rejection still lists every feature's codes, so a new feature edits the kernel and the error table. That cost is accepted for one place that maps all errors, and ADR 0012 says when to revisit it.
  • A wrong method or content type answers REQUEST_INVALID rather than a code of its own.
  • GET /api/scenes still returns the newest 100 with no paging. That needs its own design.
  • SQL keeps writing 4326 literally, as the migrations do.
  • The app was not run in a browser for this task. Nothing on screen was meant to change, and the only client change is a type.
