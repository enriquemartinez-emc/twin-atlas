Editing annotations

Task 014In progressfeat/annotation-update

Annotations can now be renamed, given new text and moved, and an edit can never silently overwrite a newer change someone else made.

Try it

With the server running, read an annotation and look at its ETag, then change it with that ETag, then try again with the old one:

curl -i localhost:8080/api/scenes/SCENE_ID/annotations/ANNOTATION_ID
# ... ETag: "0"

curl -i -X PATCH localhost:8080/api/scenes/SCENE_ID/annotations/ANNOTATION_ID \
  -H 'Content-Type: application/json' -H 'If-Match: "0"' -d '{"title":"Loose tile"}'
# 200, and ETag: "1"

# the same request again still says "0", which is now stale:
# 412 with code STALE_VERSION, and nothing is written

In the app, click an annotation in the list (or on the map in Select mode): an editor opens. Pins have a Move on map button, and the next click on the map is the new position.

What was built

  • Read one annotation. GET .../annotations/{id} returns it with its ETag, the version number in quotes (see the glossary).
  • Change one. PATCH takes only the fields that change (title, text, geometry) and an If-Match header with the version the caller read. Its kind never changes.
  • Pure rules for the update. A second use case in the functional core, in a fixed order (table below). The version check is one of them: "has this changed since you read it?" is a decision about data, so it is a plain function with a stable code, not a detail of the web layer.
  • Small, total transforms: rename, moveTo and retext, which keep the annotation's lifecycle state. A Change type (keep or replace) says what the caller wants, instead of nullable fields.
  • The stored record becomes a domain value. The conversion from database record to domain object was left out of task 005 because nothing needed it. Updating is the first thing that does.
  • One transaction. The endpoint loads the record, changes that same record, and saves, instead of rebuilding a detached one.
  • On screen: an editor for the selected annotation, "Move on map", and a "Load latest version" button that appears when someone else got there first.

Three guards, each for a different case

The pure rule handles the normal case. The database still has the last word when two requests truly race, as it did for creating annotations (ADR 0003).

Who catches itWhenAnswer
A pure ruleThe caller's version is older or newer than the stored one, which is the normal case412 STALE_VERSION
The database version columnTwo requests read the same version and save at the very same moment409 CONCURRENT_MODIFICATION
The unique title indexTwo annotations are renamed to the same title at the same moment409 TITLE_ALREADY_USED

Why it works this way

The decision to make the version check a rule, rather than an if in the controller, is written up in ADR 0010.

Found on the way

  • A title of only spaces slipped through. Signal Forms' required accepts it, so the screen would have sent a blank title and shown a server error. Tests caught it, and one shared "not blank" rule now guards the edit form, the create form and the scene name.
  • The typed message map did its job. After the contract grew five error codes, the client refused to compile until each had a readable sentence.

Not verified

The edit screen has not been run in a real browser. The page tests use a fake map and a fake HTTP layer, so they prove the flow and the requests, not how it looks or feels. A browser run needs your approval.

Known limits

  • Outlines can be renamed on screen but their corners cannot be moved yet. The API already accepts a new polygon.
  • An update cannot clear a note's text, and If-Match: * is not supported.
  • Nothing stops editing an archived annotation, because only drafts exist so far and no lifecycle rule has been needed.
  • Delete and publish are not built.
