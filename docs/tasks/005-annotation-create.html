Creating annotations

Task 005Donefeat/annotation-create

Creating an annotation is the reference example of the pure-rules design: small decisions in plain functions, the real work around them, and the database as the last line of defence.

Try it

With the server running, create a scene and then an annotation in it:

curl -s -X POST localhost:8080/api/scenes -H 'Content-Type: application/json' \
  -d '{"name":"Plaza","extent":{"type":"Polygon","coordinates":[[[2.17,41.40],[2.18,41.40],[2.18,41.41],[2.17,41.41],[2.17,41.40]]]}}'

curl -s -X POST localhost:8080/api/scenes/SCENE_ID/annotations -H 'Content-Type: application/json' \
  -d '{"kind":"MARKER","title":"Cracked window","geometry":{"type":"Point","coordinates":[2.175,41.405]}}'

The answer is 201 with the new annotation and an ETag: "0" header (see the glossary). Send the same title again and you get 409 with TITLE_ALREADY_USED.

What was built

  • Three kinds of annotation as types: a marker (a pin), a note (a pin with text) and an outline (an area). Because the type fixes the geometry, a marker with a polygon cannot even be expressed.
  • Lifecycle as types: Draft, Published, Archived. Creating produces a draft.
  • Four rules in a fixed order. The first to fail decides the answer.
  • One endpoint class with a fixed flow: load facts, decide, reject or transform, save.
  • The schema: scene and annotation tables with SRID 4326 geometry, a spatial index and check constraints, plus a unique index that backs the title rule.
  • A small scene feature (create and get), because annotations need a scene to be placed inside.

The rules and what they answer

1The scene existsSCENE_NOT_FOUND404

Why it works this way

The rules are plain functions, so they are tested with ordinary unit tests and with thousands of random inputs, without a database or a web server. Anything that can race is also guarded in the database (ADR 0003). Entities never leave the server's shell; they are mapped to plain records at the boundary (ADR 0004).

How it was checked

CheckResult
Rule tests17 table-driven cases, one for every rule and for which rule wins when several fail.
Random-input testsSix properties, each over 1000 random scenes and shapes: inside is accepted, outside is rejected, off-planet is invalid, the boundary counts as inside.
Endpoint tests on real PostGISHappy path, one test per rejection, request validation, a stale-fact case and an 8-client race (exactly one 201, seven 409, one row).
Database as final guardA test bypasses the endpoint and the database still refuses a marker with a polygon and a duplicate title.
Whole backend at the time57 tests passing, formatting clean.

Known limits

  • Only creating exists. Update, delete and publish are not built (editing is task 014).
  • The conversion from database record back to a domain object is not written yet, because nothing needs it until editing.
