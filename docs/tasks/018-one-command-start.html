One command to start the app

Task 018In progressfeat/one-command-start

One script, ./dev.sh, starts the database, the server and the client, waits until they answer, prints the address, and stops everything when you press Ctrl+C.

How to use it

From the top of the repository run ./dev.sh, then open http://localhost:4200. To check your machine first, run ./dev.sh --check: it only looks and starts nothing. I have not done a real start of the app with this script yet, and I will not without your approval.

What was built

  • One command. It starts the database with Docker (and waits until it is healthy), then the server and the client, and waits until each one answers before it says it is ready.
  • One way to stop. Ctrl+C stops the client and the server together with everything they started, then the database. The data is kept. --keep-db leaves the database running.
  • A check that explains itself. --check lists every problem it finds in plain words, with the fix, instead of failing on the first one.
  • Logs in one place. Output goes to .run/, which git ignores. If a service fails to start, the last lines of its log are shown.
  • Nothing new to install. It is a plain bash script. No package and no Docker image were added.

What the check looks at

The database port is free or already oursAnother PostgreSQL on 5432 would stop the database from starting.

Why a script and not Docker for everything

Putting the server and the client in containers would need new Docker images (a JDK, Node, a web server), use more of this laptop's 8 GB, and make client reloads slower. A script keeps the way you already work and adds no dependency. It could still be done later as its own task.

Found by your first run

You ran it and it stopped a few seconds after it said ready. The logs showed the server and the client both starting fine and then a clean shutdown, so the script itself had stopped them. The cause was mine: the script waited for either service to stop with wait -n, but the process ids had been collected in a way that made them strangers to the script. wait failed at once, I had told it to ignore failures, and the script concluded a service had died. Now the services are the script's own children, and it waits with a simple loop that checks they are alive. A small experiment reproduces the old behaviour: wait -n on such ids returns an error in zero seconds while the processes keep running.

To check the fix without starting the app, I ran a copy of the script that starts two dummy web servers instead of the API and the client. The control flow and the cleanup are the same.

Not verified

A real run of the fixed script with the database, the API and the client. That is your run, or mine if you approve it. Also still unchecked with the real app: --keep-db and installing the client's packages when they are missing.

Known limits

  • It is a bash script for Linux, WSL and macOS. It does not run in a plain Windows terminal.
  • The port check uses ss, which exists on Linux and WSL. Without it the check cannot see a busy port and carries on.
  • Logs are replaced on every run.
  • The first start is slow: the server compiles and the client builds.
