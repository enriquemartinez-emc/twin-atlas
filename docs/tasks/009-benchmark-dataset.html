Benchmark with 1M rows

Task 009In progresschore/benchmark-dataset

Does it stay fast with a million annotations on this laptop? Yes: a seeded dataset of 1.2 million rows, queried through the real API, answers most questions in 5 to 8 ms, and the spatial index is what makes that true.

Try it

scripts/benchmark/run.sh          # 1,000,000 points, 200,000 outlines, 200 runs. About 3 minutes.
scripts/benchmark/run.sh 20000 4000 20   # a quick smoke run

It uses its own database (twinatlas_bench) and port 18080, so your development data and server are untouched. It writes docs/benchmark/results.md and docs/benchmark/plans.txt. Remove the data afterwards with the command it prints.

The short version

  • Feasible here. 1.2 million annotations seed in 30 seconds. The database container used at most 800.9 MiB at the points sampled, of its 1.5 GB limit, and the server process used 345 MB.
  • Fast with the index. The 250 m view, the nearest queries and the zone query have a median of 5 to 8 ms and a p95 of about 12 ms or less. Without the spatial index the same questions take 5 to 65 times longer (the smallest gap is the 3 km view, which is slow either way).
  • Paging stays flat. Page 500 of the list (rows 99,801 on) has a median of 6.2 ms, against 5.6 ms for page 1.
  • One honest weak spot. A 3 km-wide view is slower (47.4 ms median, 92.3 ms p95), because it holds about 36,000 annotations that must all be sorted to return the first 200.

What was built

  • A repeatable seed. One SQL script with a fixed random seed. 1,000,000 points (800,000 markers, 200,000 notes) and 200,000 outlines in one scene. Real places cluster, so 80% of rows fall near one of 25 hot spots and 20% anywhere.
  • Plan capture. EXPLAIN (ANALYZE, BUFFERS) of the four read queries, with the GiST index and then without it.
  • A latency measurer in plain Node (no dependency). It asks the real API 200 questions per operation, one at a time, after 10 warm-up requests, and reports p50, p95, p99 and the maximum.
  • Memory limits recorded. The Postgres settings and the machine are written into the results file.

Why it works this way

Each decision made earlier is tested here: bounding-box test first and exact test second (ADR 0005), SQL straight to the response (ADR 0006), and paging by position (ADR 0007). The method and what it showed are in ADR 0009.

How it was checked

CheckResult
Is a million rows possible on this machine?Measured first with a throwaway table: a million points and a spatial index built in under 3 seconds, 66 MB plus a 40 MB index, 188 MB of container memory.
Do the scripts work?A small run (24,000 rows) went end to end first and caught a real bug: a lookup picked an outline where it needed a point.
Full run1,000,000 points and 200,000 outlines; seed 30 s; the whole run took under 3 minutes.
Why is the 3 km view slower?Looked at directly: it matches 36,391 rows and sorts them by time (a top-N heapsort over 15,227 buffers, 39 ms). The 250 m view matches 246 rows.
Reproducible?The seed uses a fixed random seed and the measurer a seeded generator, so a rerun asks the same questions of the same data. Timings vary a little between runs.

Not verified

Concurrent load (one request at a time was measured, not many at once). Many scenes at once (all rows are in one scene). Cold-cache timings (the data fit in memory). Other machines: every number here is this 4-CPU, 7.8 GiB laptop.

Known limits

  • A view that holds tens of thousands of annotations costs more, in proportion to how many it holds, not to the size of the dataset. A zoom-aware limit or clustering on the map would fix it. It is not built.
  • The planner estimated about 1,000 rows for that view and found 36,391: clustered data fools its statistics. The plans were still good.
  • The data is synthetic. Squares stand in for outlines.
