Client structure tidy

Task 024In progresschore/client-structure-tidy

A review of the Angular client against Angular's own recommendations found a few names and homes that did not fit. They are fixed, and nothing the app does has changed.

How to see it

Nothing looks different. Read the folder tree in How it fits together, or open client/src/app.

What changed

BeforeAfterWhy
public-api.ts, imported as @features/annotation/public-apiindex.ts, imported as @features/annotationThe old name sounded like a REST API. index.ts is the usual name for a folder's entry point. The lint rule still blocks reaching into a feature's other files; it was tried with a deliberate deep import.
map/map.service.ts, MapServicemap/map-viewer.ts, MapViewerThe last file with a role suffix. Angular's current style names a file for what it is for.
shared/problems/core/problems/Turning server error codes into messages is app-wide error handling, which is not a reusable UI part. shared/ is meant to hold no business logic.
shared/geo/geojson.tsmap/geojson.tsTwo features use these map geometry helpers, so they belong with the map code.
map/features.ts, outcome.tsfeature.model.ts, outcome.model.tsAngular keeps the .model.ts ending for plain data shapes.

One new alias

Importing @map needs its own entry in tsconfig.json, next to @map/*. The features already worked because a path ending in a folder name finds its index.ts.

How it was checked

CheckResult
BehaviourAll 243 client tests pass. Only import paths and the renamed class changed in them.
BoundariesLint passes, and a deliberate import of @features/annotation/kind-meta from the scene feature failed it with the new message.
BuildFormatting, lint with the class check and the production build are clean.

Not verified

The app was not opened after the move. The tests and the production build cover the imports, but nobody has clicked through it.
