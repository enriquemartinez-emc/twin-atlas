How it fits together

The server is one program split into feature areas. The decisions a user would care about (is this spot inside the scene? is this title taken?) live in small pure functions, and everything that touches the outside world sits around them.

Two halves of every write

A pure function only looks at what it is given and returns an answer. It cannot read a database, the clock or the network. That makes the business rules easy to test and impossible to break by accident. The shell around it does the real work: it fetches the facts, asks the rules, and saves the result. The pattern is called functional core, imperative shell.

What the build enforces

Rules about the structure are tests, so they cannot quietly rot:

  • Code in a core package cannot use Spring, Jakarta or Hibernate.
  • One feature area cannot reach into another's inner parts. Only its core is shared.
  • The platform package cannot depend on any feature area.

On the client, ESLint refuses any, imports that climb out of a folder, and reaching into another feature's files.

Where things live

FolderWhat is in it
server/src/main/java/com/twinatlas/annotationEndpoints, entity, SQL reads. core/ holds the pure rules.
server/.../scenePlain create, list and get for scenes. No rules beyond validation.
server/.../platformError format, ids and clock, GeoJSON, API documentation. core/ holds the shared Decision and Rejection types.
server/src/main/resources/db/migrationThe database schema, one numbered file per change (Flyway).
client/src/app/mapThe only code that touches Cesium.
client/src/app/featuresScreens, one folder per feature area, mirroring the server.
client/src/app/apiThe generated API client. Never edited by hand.
docs/openapi.jsonThe API contract. A server test fails when it is out of date.
docs/adrShort records of the big decisions and why they were made.
